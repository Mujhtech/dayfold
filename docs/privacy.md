# Privacy

Dayfold connects directly from this Mac to Google's authorization, user-info, and Calendar endpoints. An optional notification relay and its configured OIDC identity provider are contacted after you start Dayfold sign-in in Settings. The optional assistant connects directly to OpenAI when you send a request using your own API key. The app has no analytics or crash uploader and does not process payments; assistant API usage belongs to your OpenAI account.

Selecting Assistant mode or saving an API key does not send a model request. Sending a request transmits your text, a bounded excerpt of the previous exchange when available, the current and selected dates, display time zone and configured work hours. The assistant can then request limited downloaded calendar context: event titles, start/end times, all-day/busy flags and coverage information, or computed free-time windows. These tools include synchronized calendars hidden from the main view and exclude calendars with synchronization disabled. They do not supply Google credentials, event descriptions, guest lists, meeting URLs or provider identifiers. Any personal details you put in your own request are also sent to OpenAI.

The assistant uses the Responses API with `store: false` and does not create a server-side conversation. This is not a zero-retention promise: OpenAI's account-specific data controls and abuse-monitoring policies still apply. See [OpenAI's data usage and retention documentation](https://developers.openai.com/api/docs/guides/your-data). Requests and replies are kept in app memory rather than a persistent chat history. A suggestion becomes a saved local draft only when you choose Review Event; saving in the normal editor queues the calendar change. Changing back to Calendar mode clears the in-memory assistant exchange and cancels the active request, but cannot retract data already sent.

Assistant API keys are stored in this Mac's Keychain under a fixed OpenAI service and a hash of the local store namespace. Demo and Google stores have separate keys. Keys are excluded from preferences, calendar drafts and recovery exports. Removing a key removes this store's saved credential; it does not revoke the key at OpenAI or delete data retained by that service. Uninstalling Dayfold alone does not guarantee Keychain removal. Demo events remain separate from Google, but an explicit assistant request can send fictional demo schedule context and your request text to OpenAI.

The optional Rust notification relay in `backend/` stores verified Dayfold identity-provider issuer/subject pairs, user/device identifiers and device labels, public signing-key thumbprints, credential hashes/expiry and bounded replay/recovery receipts, opaque routing identifiers, hashed channel secrets, Google resource IDs, APNs device tokens, and reminder due/expiry times and revisions. It verifies a separate Dayfold sign-in ID token during enrollment but does not retain that token. It deliberately excludes Google Calendar credentials, event titles, descriptions, attendees, and calendar addresses. APNs reminders use generic text. This metadata still reveals reminder timing and installation activity and requires access-controlled database storage. The Dayfold private signing key, access/refresh tokens and pending enrollment/rotation recovery state are stored in this Mac's Keychain; local routing, replay and ownership state is stored in SQLite. See [native relay setup](relay.md) and [backend setup and privacy boundary](../backend/README.md).

Google authorization archives, including refresh tokens, are stored in Keychain under a client/store/account-specific service. The provisioned app uses its private data-protection Keychain identity; the ad hoc development build uses the login Keychain. Migration verifies the new item before removing its predecessor. SQLite contains account references and permitted calendar data, drafts, pending changes, conflict baselines, and search text. Store directories use private filesystem permissions, together with the application sandbox and the user's OS protections. Cache data is not separately encrypted with SQLCipher or end-to-end encryption. See the [security boundaries and release requirements](security.md).

Production and demo data are stored separately in the application's Application Support container. Demo identities use example.com and fictional content. Local HTTP sessions use ephemeral configuration without a URL cache. Ordinary diagnostics contain versions, state categories, counts, and timings; they exclude tokens, descriptions, guest lists, and meeting secrets.

Descriptions render as plain sanitized text. They do not execute scripts or fetch tracking images. Meeting/attachment links open only after a user action and scheme validation. Multiple meeting destinations are presented as choices. Browser sign-in identity is independent of the calendar identity.

Recovery exports intentionally contain personal calendar drafts and pending intent. The export panel explains this; exports contain no OAuth credentials and are not automatically replayed. Disconnect can export before explicitly discarding account-local work, removes credentials/cache/search/reminders, and never deletes Google calendars. Uninstalling the application alone does not guarantee removal of its container or Keychain entries.

Reminders are optional. OS preview policy applies, with an optional stricter Busy event title. macOS can deliver already-scheduled reminders after the app quits. The relay supports APNs from previously uploaded schedules, but public user sessions keep this disabled until push-destination possession is verified; the relay does not fetch calendar changes itself. Dayfold cannot update schedules while quit, asleep, or offline. Disconnect confirms server revocation before clearing local relay ownership and credentials; it does not delete Google events.

Dayfold account deletion removes the relay identity, device sessions and their stored routing/schedules. To confirm deletion cleanup after a lost response, bounded confirmation receipts retain refresh-token hashes, public-key thumbprints and expiry for up to seven days, without user/device/issuer/subject links. Short-lived proof replay records expire separately. These records are security metadata, not anonymous data. It does not delete the account at your identity provider, Google calendars or files you exported. Security logs contain opaque user/device IDs and action outcomes, not credentials or calendar content; deployment-specific retention and backup deletion must be established before public release.

Authentication response recovery lasts five minutes, while metadata retention is longer: consumed enrollment receipts keep the ID-token hash and verified identity/key binding for up to 30 days; revoked session families and issuance hashes are eligible for cleanup after seven days. Account deletion removes identity-linked enrollment/session records immediately in its transaction. Proof replay records expire at the proof timestamp plus 60 seconds. Expired records cannot authenticate; bounded periodic cleanup makes physical removal eventual, and production backup/log retention needs a separately enforced policy.
